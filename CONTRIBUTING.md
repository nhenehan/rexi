# Contributing to rexi

This document covers the crates, build and test commands, generated files and third-party test dependencies.

## Crates

| Crate | Purpose |
|---|---|
| `rexi` | Facade: re-exports rexi-core, and rexi-schema, rexi-xml and rexi-serde by feature |
| `rexi-core` | Codec core with no dependencies: bit I/O, datatypes, string tables, grammar runtime, `Encoder`/`Decoder`, header and options document. `no_std` + `alloc` |
| `rexi-schema` | XSD to `GrammarSetBuf` tables (roxmltree) |
| `rexi-schema-gen` | XSD to a `static GrammarSet<'static>` (Rust source) |
| `rexi-xml` | XML to events and back (quick-xml), and the `rexi` CLI |
| `rexi-serde` | Serde `to_exi`/`from_exi`; the grammar decides attributes, namespaces, choices and value types. `no_std` + `alloc` |
| `rexi-capi` | C ABI, `librexi.a`/`.so`, header regenerated by cbindgen on every build (commit it with the source change) |
| `rexi-tests` | Conformance tests against EXIficient reference bytes, with exipd as judge |
| `rexi-nostd-check` | Uses core and serde from a `#![no_std]` crate, built for `thumbv7em-none-eabihf`, tested on the host |

### Features and tables

- **`std` feature.** The default `std` feature of rexi-core and rexi-serde only makes every `std::io::Read`/`Write` an `io::ByteSource`/`io::ByteSink`. Without it, `&[u8]`, `Vec<u8>` and `io::SliceSink` are the sources and sinks. Depend with `default-features = false`.
- **Tables.** Grammar tables are flat slices indexed by `u32` newtypes (`UriId`, `ElemIdx`, ...). Reading static tables never allocates; the codec allocates its string table when an `Encoder`/`Decoder` is built.
- **Examples** and `fuzz/` are separate workspaces, built only on request.

## Untrusted input

Decode limits:

- `max_depth`: 256
- `max_list_items`: 1,000,000
- `max_integer_bits`: 4096
- `max_string_bytes`: 256 MiB

Change them with `DecodeLimits` and `Decoder::with_limits` (or the `*_with_limits` functions of rexi-xml and rexi-serde), `RexiLimits` and `rexi_decoder_new_with_limits` in C, or `--max-depth N` and friends (`--no-limits`) in the CLI.

Schema rules:

- Includes and imports read only regular files under the main schema's folder, at most 16 MiB each. URLs, pipes and devices are not allowed.
- A location outside the folder is refused before any file is touched, so errors never tell which files exist.
- Sets like UBL (`../common/...`) can set a root with `SchemaLoadOptions` and `compile_files_with`, `rexi_tables_from_xsd_with_root`, or `--schema-root DIR`.
- Breaking a rule gives `SchemaError::Refused`.
- One type's content may expand to at most 100,000 grammar rules (`max_grammar_size`, else `SchemaError::TooLarge`).
- Circular groups are refused.

## Gate and commands

`scripts/gate.sh` runs everything a commit must pass: the first eight commands below, plus the generated-table and EXIficient fixture checks. `--quick` skips the fixtures, which need Java.

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --no-deps
cargo test --workspace
cargo clippy -p rexi-core -p rexi-serde -p rexi-nostd-check --all-targets --no-deps --no-default-features
cargo test -p rexi-core -p rexi-serde -p rexi-nostd-check --no-default-features
cargo build -p rexi-nostd-check --target thumbv7em-none-eabihf   # rustup target add thumbv7em-none-eabihf
cargo +1.88 test --workspace   # oldest supported Rust (rust-version); rustup toolchain install 1.88
cargo run -p rexi-xml --bin rexi -- encode --xsd a.xsd in.xml out.exi
cargo run -p rexi-xml --bin rexi -- decode --xsd a.xsd out.exi
cargo run -p rexi-xml --bin rexi -- decode --xsd a.xsd --max-depth 1024 out.exi   # or --no-limits
cargo run -p rexi-schema-gen -- a.xsd [b.xsd ...] --out tables.rs [--name GRAMMARS] [--schema-id ID] [--check]
fuzz/run.sh [seconds]   # fuzz targets, 60 s each by default (nightly, cargo install cargo-fuzz)
```

`cargo test -p rexi-capi` builds and runs the C smoke test in `crates/rexi-capi/tests/c` with CMake, ASan and UBSan.

## Generated tables

Generated tables are a module (`mod tables;`), not an `include!`, because they start with inner attributes.

Each declared element and attribute name gets a `pub const LN_<NAME>: QNameId`.

`scripts/gen-tables.sh` regenerates the test statics in `crates/rexi-tests/src/generated` (`--check` verifies them), and `fixtures_strict_static.rs` runs the strict fixture gate through them.

## Reference fixtures

`scripts/gen-fixtures.sh` regenerates the reference bytes in `crates/rexi-tests/fixtures/interop` with EXIficient 1.0.7 (from Maven Central), through the pinned exip's oracle `utils/xsd2exip`, a Maven project that `scripts/fetch-third-party.sh` checks out.

See `cases.tsv` and `manifest.tsv` there; the manifest records a hash of the oracle sources. `--check` verifies the committed files are unchanged. Reference bytes change only on purpose (`--force`).

## Third parties

Nothing third-party lives in the working tree. `scripts/fetch-third-party.sh` checks out the commits pinned in `third-party.lock` (exip, for the exipd judge and its test set, and the W3C exi-testsuite) into:

```text
${REXI_THIRD_PARTY:-${XDG_CACHE_HOME:-~/.cache}/rexi/third_party}
```

```bash
scripts/fetch-third-party.sh --build         # fetch pins, build exipd and the oracle jar
scripts/fetch-third-party.sh --check         # every checkout present, clean, at its pin
scripts/fetch-third-party.sh --update exip   # on purpose: re-pin to remote HEAD
```

Tests that need exipd or exip's test data skip when the cache is empty. Set `REXI_REQUIRE_JUDGES=1` to make them required.

## W3C strict group

`scripts/w3c-strict.py` runs the W3C test suite's strict group (`config/testCases-interop/strict.xml`: schemaValidDatatypes and declaredProductions, 219 cases) from the cached exi-testsuite. EXIFormat.jl has the same script, which drives `bin/exiformat`: keep the two copies the same. For each case, on bit-packed and byte-aligned, EXIficient (the oracle jar) makes the reference stream and its events; rexi's encode must give the same bytes, its decode the same events, and decode then encode the same bytes again. The references are made at run time under `target/w3c-strict/`; nothing from the suite is committed.

```bash
cargo build --release -p rexi-xml --bin rexi --features wildcard
scripts/w3c-strict.py                        # compare with scripts/w3c-strict.expected
scripts/w3c-strict.py --update               # on purpose: accept the new results
scripts/w3c-strict.py --report r.md          # also a table of every result
```

The run fails when a result differs from `scripts/w3c-strict.expected`, both when a case stops passing and when one starts. When a change makes cases pass, run `--update`, check the diff, and update the README's conformance row. CI runs it in the `exificient` job.

## Releasing

1. Bump the version in `[workspace.package]` and in the rexi entries of `[workspace.dependencies]` in `Cargo.toml`, and add a `## X.Y.Z - YYYY-MM-DD` section to `CHANGELOG.md`.
2. Push to `main` and wait for CI to pass.
3. Push the tag `vX.Y.Z`. The release workflow (`.github/workflows/release.yml`) runs CI again, checks that the tag matches the version, and then waits for an approval of the `crates-io` environment on the run's page. After the approval it publishes every crate to crates.io and makes the GitHub Release from the CHANGELOG section.
4. If crates.io stops the publish partway (for example its limit on new crates), use **Re-run failed jobs** on the run: crates whose version is already on crates.io are skipped.
